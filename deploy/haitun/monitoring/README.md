# 生产持续监控 · 投递骨架与第 1-3 类指标 + 成本节

**报告不能跑在被监控对象里。** 这是本目录存在的全部理由, 其余设计都是它的推论。

故障史里最贵的一次是 gateway 502 持续 **29 小时无人知晓**。若日报靠 gateway 自己的
schedule runner 发, gateway 挂了日报也挂 —— 恰在最需要告警时静默。所以: **宿主 cron +
独立出站 webhook**, 不经 gateway、不经 psi-agent 任何进程、不 import 内核(内核在容器里、
日报在宿主, import 不过去, 而且**故意**不过去)。

用飞书**自定义机器人 webhook**(纯 HTTP POST), 不用 app token —— app token 走 OAuth,
而 OAuth 回调正是坏过的那条路。监控不能依赖它监控的东西。

## 数字进表, 消息只在有事时来

日报的主载体是**多维表格**: 一天一行, 一指标一列, 重跑更新那一行而不是追加。消息只在有异常
**或有观测缺口**时发, 纯文本 + 表链接。

为什么不每天发一条全量报告: 那样的结局是被无视, 然后被静音 —— 静音之后这套监控等于不存在。
日报的存活证明因此落在**表里有没有今天这一行**上。

### 表里「没量到」是空格子, 不是 0

这是整个写表层唯一要守住的事。表的读法是竖着看一列, 所以一格 0 与一个真实的低读数**不可
区分**, 折线图还会把它画成一次暴跌。文字版至少还有「未测到」三个字。

三道挡: `Finding` 构造期拒绝 `UNKNOWN` 带数字(且**先报这一条**再报「缺告警线」—— 反过来会
把人引向「补个 num_warn」, 补完就静默通过)、`_measured` 再滤一遍、`build_row` 对没量到的列
**整个 key 不写**。

### 卡片那条路删了

曾用飞书交互卡片 + 资源占比条形图。删的原因是**图上一根共用告警线在各项告警线不同时会画出
假越线**: 实测磁盘 81% 的柱子越过「告警 80%」那根线, 而它自己的线是 85%。改成每项配自己的
告警线之后又撞上 VChart 的 `seriesField` 默认**堆叠**, 87+85 画成 172。

读图的人先看柱子与线的相对位置, 再看标题, 所以一行说明修不了它。趋势交给表, 消息只说事。
顺带去掉的失败面: 卡片 schema 变更、chart 组件要求客户端 7.1+、整卡 30KB 上限 —— 这三种
失败的表现都是群里安静, 与一切正常不可区分。

## 三档与为什么是三档

| 档 | 频率 | 内容 | 为什么 |
| --- | --- | --- | --- |
| 日报 | 每天 8:57(非整点) | 全量采集 → 写表一行; 有异常才发消息 | 整点扎堆会命中上游限流 |
| 即时 | 5 分钟 | 公网可达性 + OOM | 502 那次若只靠日报 = 等 24 小时 |
| 心跳 | 每天 9:03 | 即时档过去 24h 跑了多少轮 | 即时档只在有异常时出声, 它自己死了同样是安静 |

**全绿时刻意不出声** —— 5 分钟一条会被无视继而被静音, 静音之后连真告警也收不到。即时档的
存活由心跳那档保证, 且心跳**报轮数不只报存活**: 轮数少于预期(约 288)是 cron 漏跑的唯一线索。

## 投放(由负责人做, 不在卡的范围内)

```bash
# 1. 脚本
install -d /srv/haitun/monitoring
cp -r deploy/haitun/monitoring/* /srv/haitun/monitoring/
chmod +x /srv/haitun/monitoring/cron-wrap.sh

# 2. 配置(凭据, 0600)
install -D -m 0600 monitoring.conf.example /etc/haitun/monitoring.conf
vi /etc/haitun/monitoring.conf     # 填 webhook_url / vhosts / public_ip
                                   # 另填趋势表四项: feishu_app_id / feishu_app_secret /
                                   # bitable_app_token / bitable_table_id
                                   # 应用凭据可直接从 gateway 容器里读, 不必另建应用:
                                   #   docker exec psi-agent-gateway printenv \
                                   #     PSI_FEISHU_APP_ID PSI_FEISHU_APP_SECRET
                                   # 表和列不用手建: 先建一张空多维表格、给该应用编辑权限,
                                   # run.py 每次跑会把缺的列补齐(已有列一个都不碰)

# 3. 先验投递链路再装 cron —— 否则「webhook 配错」会以「日报没来」的形式出现,
#    而那与「一切正常」不可区分。
/srv/haitun/monitoring/cron-wrap.sh selftest

# 4. 核时区(见下), 然后装 crontab
date
crontab -l > /tmp/cur && cat crontab.example >> /tmp/cur && crontab /tmp/cur
```

### 时区: 宿主时区, 不是容器时区

`crontab.example` 里的时刻是**宿主本地时间**。容器里那套时区只由 compose 的
`TZ=Asia/Shanghai` 撑着, 容器内 `/etc/localtime` **恒为 UTC** —— 拿它当判据会得到「UTC」
这个假阴性, 然后据此把时刻调偏 8 小时。已经因此漏检过一次定时任务静默偏移。装之前
`date` 一次。

## 每个指标都带「上次它怎么骗过我们」

**这一列不能删。** 没有它, 后人会把这些看似多余的断言当冗余删掉, 然后把同一个假阴性
判据再写一遍。

### 第 1 类: 公网可达性

| 指标 | 上次它怎么骗过我们 |
| --- | --- |
| 每个 vhost 的公网 HTTPS 状态码 | 502 那 29 小时**容器内自检全绿**, 只有从外面打才算数 |
| OAuth 回调实打一次 | 定时任务与发卡片走**出站**, 回调走**入站**; 内部全绿不证明入站活着 |
| TLS 证书剩余天数 | `caddy validate` 绿而 reload 失败, 服务仍 active 跑**旧配置**, 新 vhost 静默没生效。故从**真实握手**取, 不读磁盘 |
| 飞书 wss 数 | **wss=0 只证明收不到, 不证明发不出** —— 只起 gateway 也会真发飞书卡片。报告里带这句语义, 否则读者往反方向查 |
| 8090 实打 | netns 死了 8090 照样 `LISTEN`; `Up` 与 `LISTEN` 是两个并列的假阴性, 只有**真打一次请求**算数。另: **8090 是 oauth-proxy 不是 gateway**(gateway 在容器内听 8080), 混了会得出反向的错误根因 |

**硬要求: `curl --resolve`, 不是 `-H Host`。** 后者只改 HTTP 头, TLS 握手的 SNI 仍是裸 IP,
服务端在 TLS 层就 alert, curl 报 `HTTP=000` —— 而 `000` 与真 502 **不可区分**, 会假报一次
服务宕机。判据 `test_vhost_probe_uses_resolve_not_host_header` 断言命令行本身, 因为这个
缺陷只在命令行上看得见(跑起来之后两者都只是「连不上」)。

### 第 2 类: 资源与 OOM

| 指标 | 上次它怎么骗过我们 |
| --- | --- |
| `dmesg` 里 OOM kill 计数 | gateway memcg OOM 撞 3g 时**三处判据全假阴性**(OOMKilled=false、容器 Up、日志像上游问题), 只有 `dmesg` 靠得住 |
| 可用内存 / swap | A 机搬来 ToC 后可用仅 1.6G 且 `swappiness=0`; **B 零 swap 而 A 有 4G**, 故 swap=0 在 B 上是常态不是回归 |
| `swappiness` 的**声明值** | 阿里云 `sysctl.d` 显式声明 0, `sysctl -w` 只改运行时、**重启必回滚**。故同时报运行时值与声明值, 且声明值取**加载顺序里最后一个** |
| 各容器 memcg peak | 子进程被 OOM 杀掉时 `OOMKilled` 仍是 **`false`**, 状态 Up, **零告警**。故**不用 `docker inspect` 判 OOM**; 峰值读不到就报「未测到」, **不拿瞬时值顶替** |
| 磁盘 / inode | 两条分开 —— inode 耗尽时空间可能还很空, 而报错同样是 `No space left on device` |

另: `docker logs --since` 写 `HH:MM` **静默失效**(只吐一行错误消息, grep 完看着像「没
触发」), 必须写完整时间戳。本目录目前没用到它, 记在这里防复现。

## 报告可读性的三条硬要求

1. **异常排最前, 正常压一行。** 日报最大的失败模式不是数字错, 是没人读;
2. **每个指标带基线与方向。** `232 of 232` 单看无异常, 只有知道应是 66 才叫异常 ——
   没有基线的数字不会触发任何人的警觉。故 `Finding` 把这两个字段做成**必填**;
3. **「未测到」与「零」两栏, 不混。** 量 `live render` 得 0 行不是没渲染, 是那行为 DEBUG
   而生产跑 INFO —— **观测缺口伪装成健康**。`UNKNOWN` 不给 `reason` 在构造期就抛。

三条在消息与趋势表两个载体上都成立 —— 换载体不换规则。表上第 3 条多一层:
**「未测到」在表里是空格子, 不是 0**。一格 0 与一个真实的低读数不可区分, 折线图还会把它画成
一次暴跌 —— 而一列数字里没有「未测到」这个形态。`Finding.num` / `extra_nums` 在 UNKNOWN 时
非空即构造期报错, 且那条检查**刻意排在「缺告警线」之前**: 先报缺线会把人引向「补个 num_warn」,
补完就静默通过。

表里一指标一列, 同类**取最严的一个**(三个容器内存合成一列峰值, 不取平均 —— 平均会把「三个
里有一个撞到 95%」抹平)。是哪个容器看 `越线项` 那一列。

### 第 3 类: 请求成本与延迟

来源是三个容器的 metrics jsonl(一人一容器, 所以容器≈人)。**三份都读**, 缺哪份报「未测到」
而不是当 0 —— 跳过的话那个容器整个从报告消失, 而消失与「这人今天没用」不可区分。
`metrics/` 是新建目录, **首次部署前它不存在**, 那条路径必须正常出报告。

| 指标 | 上次它怎么骗过我们 |
| --- | --- |
| 请求体**字节数** p50/p95 | 首字延迟 ≈ 字节数 ÷ 带宽(单流约 230KB/s), 是最有解释力的单一指标。裁上下文要按**字节**不按字符 |
| `tools_exposed=N of M` **比值** | `232 of 232` 表示收窄没生效, 而日志同时汇报「机制已启用」;**光看 N 看不出来**。`66 of 66` 是能证明判据真在比比值的唯一入参 |
| 工具 schema 字符数 | 曾实测 289774, 占不可裁地板约 47%。**埋点当前没有这个字段**, 故报「未测到」并写明缺口 —— 不拿个数乘估计值冒充实测 |
| 首字延迟 | **不能用 `AI response status: 200`** —— 那只有 50-60ms, 量的是 litellm 立刻回的 SSE 响应头。用 `turn` 行的 **`ttft_s`**(方案文档写的 `ttft` 是错的) |
| 压缩耗时与次数 | 曾实测 41.5s x 22 次。读 `event="compaction"` 行 —— 压缩独立一行, 不并进触发它的回合 |

### 成本一节

四个数各带基线与方向: 当日总花费、每回合成本 p50/p95、压缩占总花费比例、**「未测到 usage」
回合占比**。三条硬要求:

1. 打印**必须带单价表版本号**且带「**未与账单对过**」。本期不做对账(负责人已定), 这是唯一
   的诚实性保障。版本号同时跟着指标条目走 —— 正文可能被超长截断, 而条目排在前面;
2. **缓存命中不省字节, 只省钱。** 首字延迟由上传带宽决定。两件事**分节写**: 字节/延迟在第
   3 类, 缓存命中率只在钱这一节, 谁也不解释对方;
3. **「未测到 usage」的回合不得静默算作 0 元。** 报告明说「N 个回合无 usage, 总花费是
   **下限**」。`Bucket.amount` 只累加算得出的行, 算不出的进独立计数。
