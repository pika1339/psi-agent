# 晨会汇报

每周一、三、五晨会之前, 按开会 SOP 把要汇报的内容分成五个分支. 本文是这条汇报的 skill.

五个分支, 顺序固定:

1. 困难点 / 风险点 — **已特化** (下面两条规则)
2. 做得好与不好的地方 — **已特化** (复用正负面清单, 写行为品质)
3. 结果, 以及和成果的关系 — **已特化** (每条 TODO 一句承诺; 成果是工作树往上约两层)
4. SOP 化和 SOP agent 化的情况 — **已特化** (先写清定义, 再按海豚自身执行记录说明几条基本 SOP)
5. 手头方案 / 评测的情况 — **已特化** (只留接口, 联动方案 SOP skill)

**刻意为之:** 第 5 维不在本文重写方案或评测口径. 第 4 维的 agent 化三层是定义, 不要改成别的打分体系.

## When to use

- 周一、三、五晨会之前, 或用户说「帮我梳理要汇报的」「晨会要说什么」.
- 用户点名困难点、风险点, 或问手头工作和上层工作有没有对上.
- 用户要写「做得好 / 不好」, 或草稿里只有某件事、某次交付的好坏.
- 用户要写结果、结论、和成果的关系, 或某条 TODO 还没有一句话结论.
- 用户要汇报 SOP 化、SOP agent 化, 或问某条 SOP (方案 / 决策等) 海豚做了什么.
- 用户要汇报手头方案、评测方案、评测数据, 或方案跟进到了哪一步.

## When not to use

- 判 todo 填没填、做完没、真不真、闭环 — 各有专门 skill, 不要用晨会稿代替那些判定.
- 用户只要写或改方案全文、不要晨会稿 → 直接用 [`proposal-writing-standard`](../proposal-writing-standard/SKILL.md). 晨会里的方案/评测段仍走本文第 5 维, 写的时候再读对应 skill.
- 用户明确要把一条行为写入正负面清单正式总表 → 走 [`positive-negative-list`](../positive-negative-list/SKILL.md) 的录入流程. 晨会稿只识别和改写, 不写表.

## 第 1 维 · 困难点 / 风险点

困难点和风险点是现实里的事, 海豚不自己到现实里找. 除具体开发以外的活尽量在海豚里做, 所以开发路径和卡住的点应该已经在对话里; 工作挂在哪一层, 在工作树上. 本维只做下面两条.

### 规则 1 · 近两天对话

回顾近两天的对话上下文. 材料是本会话里已经看得到的历史 (含压缩摘要里还能对上日期的近期内容). 扫三类:

- 之前搁置的问题
- 讨论过的问题点
- 还没拍板的点

对每一条只确认它现在有没有解决.

- 解决了: 标已解决, 汇报里只留标题, 不展开.
- 没解决: 留在汇报里, 当作困难点, 并注明它来自哪一段对话.

对话窗口盖不住近两天时, 写明实际盖住了哪一段. 没看到的日子不要写成「没有困难」.

### 规则 2 · 本人子工作树与上层的联系

海豚能看到公司工作树 (飞书思维笔记). 用 `feishu_worktree_read` 检索 **属于当前用户** 的全部子工作树:

- `user_key` 用 `<feishu_context>` 的 `sender_open_id`, 只保留 `open_id` 对上的条目.
- `mindnote_token` 用工作树的 `obj_token`. 手上是 `/wiki/` 链接时, 先经 `feishu_api` 打 `GET /open-apis/wiki/v2/spaces/get_node`, 取 `obj_type=mindnote` 的 `obj_token`.
- 缺 `mindnote:node:read` 时走 `feishu_auth_request(capabilities="mindnote_read")`. 授权没完成就不要把这一条当成「没有风险」跳过.

每条返回路径是从根到当前节点. 对每一条当前工作, 要能说出它和 **上一层**、以及再往上 **一层** (上两层) 的工作各是什么联系. 联系必须能从这条路径或近两天对话里指出来.

- 指得出来: 写一句联系, 附路径.
- 指不出来: **就是风险点**. 写明缺的是上一层还是上两层, 不要编一条联系圆过去.
- 节点上面没有那么多层 (已经在根下第一层或第二层): 写明「没有上一层」或「没有上两层」. 层数不够不是风险.
- 工作树没读到 (没有 token、未授权、空树、调用失败): 这一条本身记成风险点「工作树未读到」, 不要当成「所有工作都接得上」.

## 第 2 维 · 做得好与不好的地方

识别对话里的好与不好, 复用 [`positive-negative-list`](../positive-negative-list/SKILL.md) 的判定口径: 先 `positive_negative_rules` 查当前这件事, 行为性质和主条目以返回的规则为准, 不自造规则名, 不展示规则 ID. 只复用识别和分类. 不写正式总表, 不计分, 不排名, 不发卡.

### 原则

晨会这一维写的是共性, 不是某一次产出:

- 不写自己做的工作质量高或不高.
- 不写某件事好或不好.
- 「好」要落在正负面清单 SOP 的行为品质上, 例如积极响应、积极对齐、勇于担责, 以及规则库返回的同类正面条目.
- 「不好」也必须是共性的行为: 符合或违反工作流程、违反 SOP 的行为. 不写成「这件事没做好」.

规则库的中文条目名和上面三个例子不一致时, 用规则库的名字. 例子对不上任何返回条目时, 标「口述品质, 规则库没有对应条目」, 不要假装命中.

### 对方写的是事, 就把逻辑链补齐

对方草稿或对话里只有一件事 (做了某功能、某次交付、某次协作) 时, 不要原样放进汇报. 按正负面清单的好坏内容, 把链补成三截:

1. **事** — 只作例子, 一句话.
2. **行为** — 这件事里可观察、换一件事仍成立的行为.
3. **SOP** — 该行为落在哪条正面行为品质, 或哪条违反 SOP 的共性上. 负面同时写清单里的正确做法.

补不齐 (只有「质量高/质量不高」或「这件事好/不好」, 没有可观察行为, 也没有规则条目) 时, 告诉对方缺的是哪一截, 晨会稿里不收这句.

材料仍是近两天对话里已经看得到的内容. 窗口盖不住就写明盖住了哪一段.

## 第 3 维 · 结果, 以及和成果的关系

结果和成果不是一回事.

- **结果**是当前阶段做出来的最终结论, 一句话. 评测就是概括数据, 并写出数据说明什么. 例如 B 端评测: 「450 条过了 xx 条, 说明可以用 / xx 方面要加强.」对话或文档里已经有数字, 就把 xx 填上, 不要留空.
- **成果**是工作树上大约再往上两层的那件事. 关系只有一种: 这个结果对那件事做了什么赋能.

结果的说法是承诺:

- 这条 TODO 完成了: 承诺这件事已经符合标准.
- 还没完成: 承诺在某个时间给出后续, 或在某个时间彻底完成. 时间要写出来.

海豚看得到汇报人的 TODO 和工作树, 所以按此人当前阶段的每一条 TODO 各写一条, 不要并成一段总述. 工作树用 `feishu_worktree_read`, 只取 `@` 到本人的节点; TODO 以当期这条工作的说法为准 (填报、对话、交付文档里对得上的那条).

### 有没有交付文档

对每一条 TODO:

- **有交付文档** (飞书文档或工作区里这份交付): 概括文档内容. 文档里没有结论, 就补一句结论. 过了海豚的文档应该有结论; 补的时候标明这句是补上的.
- **没有交付文档**: 用和海豚的工作对话概括当前任务做到哪一步, 并给出后续开发方向的结论, 以及相应的时间.

两条都按上面的承诺语义来写. 完成了就写已经符合哪条标准; 没完成就写在什么时间给出后续或彻底完成.

### 成果关联

每条结果写完后, 找到这条 TODO 对应的工作树节点, 沿路径往上看大约两层, 写出成果, 以及这个结果如何赋能那件事. 层数不够就写到实际有的那一层, 并写明上面没有更多层. 节点对不上、或说不出赋能, 就标明缺关联, 不编一条赋能.

## 第 4 维 · SOP 化与 SOP agent 化

SOP 的 agent 化本身就是当前海豚在做的事, 海豚手里有充足的数据来源. 这一维由海豚代劳说明, 先按下面的定义写, 再落到几条基本 SOP (如方案 SOP、决策 SOP) 的实际情况. 不要用常识另造一套「SOP 成熟度」或「自动化百分比」.

### 定义 · SOP 化

**SOP 化**指每个员工做事时, 通过 SOP 做「公式化打法」, 从而在一些环节上不因自己的判断而出错.

- 某个环节**没有按 SOP 执行** → **未 SOP 化**.
- 某个环节**严格执行 SOP** → **SOP 化**的表现.

汇报这一维时, 先说清汇报人近期相关环节是按 SOP 走的, 还是某一环跳过了 / 凭自己判断了. 材料来自近两天对话、相关 skill 的执行痕迹、以及海豚自己做过的审查与提醒. 不要只写「我们有 SOP」而不说有没有按它做.

### 定义 · agent 化 (三层)

**agent 化**指在 SOP 的执行过程中, **agent (海豚) 做了什么**. 分三层, 顺序固定, 不要合并成一句「海豚帮忙了」:

1. **省力活 (强制)** — 执行 SOP 的过程中, 海豚要帮助干一些省力的活. 这一层是强制的. 汇报时写清: 这条 SOP 里海豚替人干了哪几段省力活 (例如查表、组卡、填模板、拉名单).
2. **补到 80 分** — 人没做到 80 分的部分, 海豚按 SOP 内容审查并补到 80 分. 例如 TODO 缺内容、方案缺友商对照. 汇报时写清: 缺了什么、海豚按哪条 SOP 补了什么. 没补过就写「本轮没有补分动作」, 不要假装补过.
3. **未遵循则提醒** — 人没有按 SOP 行动时, 海豚予以提醒. 例如预备期提醒 (方案入口那一层). 汇报时写清: 提醒了谁、对应哪条 SOP、提醒的是哪一环. 没有触发过提醒就写明没有, 不要编一条提醒记录.

三层都是 **agent 化的实现形式**. 某一层本轮没有发生, 就如实写没有, 不要用相邻层顶替.

### 落到几条基本 SOP

用上面两套定义, 说明汇报人近期相关的几条基本 SOP 的 agent 化情况. 至少覆盖手头对得上的, 例如:

- **方案 SOP** — 入口提醒、撰写检查与友商对照、跟进与验收相关 skill (见第 5 维接口表).
- **决策 SOP** — 大事 / 中事 / 小事分级与是否先写方案 (见 [`proposal-need-remind`](../proposal-need-remind/SKILL.md)).

还有别的 SOP 且近两天对话或执行痕迹能对上, 同样按「SOP 化有没有按环节执行 + agent 化三层各做了什么」写. 对不上的 SOP 不要硬写一整段空话.

## 第 5 维 · 手头方案 / 评测

海豚会跟测评方案、测评数据、方案撰写, 以及方案过程的监督. 这一维不另写一套口径. 晨会稿只留接口: 先读下面对应的 skill, 再按那个 skill 的口径写这一段.

| 手头这件事 | 读 |
|---|---|
| 方案要不要写、过程提醒 | [`proposal-need-remind`](../proposal-need-remind/SKILL.md) |
| 方案撰写、检查、补救、跟进定时 | [`proposal-writing-standard`](../proposal-writing-standard/SKILL.md) |
| 评审建议档位 | [`proposal-review-standard`](../proposal-review-standard/SKILL.md) |
| 评测 / POC 材料对照方案 | [`proposal-acceptance-poc`](../proposal-acceptance-poc/SKILL.md) |
| 交付文档对照书面标准 | [`proposal-acceptance-doc`](../proposal-acceptance-doc/SKILL.md) |
| 海豚功能评测数据 | [`haitun-feature-uat`](../haitun-feature-uat/SKILL.md) |
| 评测里的接线 / 静态复现 | [`poc-l2-reproduce`](../poc-l2-reproduce/SKILL.md) |

一份方案或一次评测对上哪一行, 就加载哪一个, 用它的结论写晨会这一段. 写不出时标明缺的是方案、评测数据还是过程记录, 不要在本文里现编四期结构、及格线或通过结论.

## 产出

五个维分开写.

第 1 维四块:

1. 未解决的搁置 / 讨论点 / 未决策 (每条带来源)
2. 已解决的, 只列标题
3. 和工作树上一层或上两层说不出联系的条目 (路径 + 缺哪一层)
4. 工作树没读到时的那一条风险

第 2 维每条三截: 事 (例子) / 行为 / SOP 行为品质或违规. 好与不好分开. 没有可落点的句子不收.

第 3 维每一条 TODO 一块: 一句话结果 (承诺语义, 有数据就写上) / 来源 (交付文档概括, 或对话里的状态加后续方向和时间) / 往上约两层的成果以及赋能. 对不上的标明缺关联.

第 4 维每一条相关 SOP 一块: SOP 化 (哪些环节按了 / 哪些没按) + agent 化三层 (省力活 / 补到 80 分 / 提醒). 没有发生的层如实写没有.

第 5 维每一份手头方案或评测一块: 用上表对应 skill 的口径写现状. 不在晨会稿里重写那份 SOP.

没有命中就写「近两天对话里没有未决点」「本人工作树条目都能指向上层」「近两天对话里没有能落上正负面清单的行为」「当前没有可概括的 TODO」「近期没有对得上的 SOP 化 / agent 化痕迹」或「手头没有在跟的方案或评测」.
