# 可观测性埋点与生产监控日报 · 方案

> 本文只写设计，不含实现代码。所有数字均为既有实测结论，本文不重新测量。
> 落地拆卡见文末「分卡与依赖」。

## 一、结论先行

现在的可观测性只有外壳：从公网打和从宿主机看资源能看见，系统内部基本是黑的。

按 trace / log / metrics 分：
- **log 有，但关键信号躺在 DEBUG**，而生产跑 INFO（`_run.py` 把批量模式的级别钉死在 INFO，
  生产走的正是批量模式，因此生产**没有任何路径能开出全局 DEBUG**）
- **metrics 为零**。所有数字都是某次排查的手工快照，没有历史因而没有基线
- **trace 接近 0**

**成本是完全的盲区**——没有任何一处记录一个回合花了多少钱。L1 框架写了「单任务 < ¥0.3」这个
目标值，而当前连分子都没有。

本期做 metrics、log、成本三块，外加生产持续监控日报。**不做 trace**——trace 要求贯穿 id 穿透
内核 / provider / 工具三层，而内核边界尚未收敛（haitun 反向依赖内核 19 处），穿不下去，
排在边界收敛之后。

### 与草案的三处订正（开工前已实测核对）

草案假设首字延迟与工具收窄比值都要新建埋点，实测已经存在：

| 草案说法 | 实测 | 因此本期要做的是 |
| --- | --- | --- |
| 首字延迟要新建采集 | `session/ai_client.py:152` 已有 INFO 行 `AI first token: ttft=… req_bytes=… kind=…`，PR #972 落的。同文件 `:86` 那行还专门注了「非首字」 | 把已有点位**接到 jsonl**，不是新建 |
| `N of M` 要新建 | `session/tool_exposure.py:181` 已在 INFO 打 `N of M` | 同上，接线 |
| 压缩耗时要接线 | `session/_compaction.py` **一行 logger 都没有** | 这是唯一需要从零加点位的地方 |

其余为零的：`src/psi_agent/metrics.py` 不存在；`docs/plans/` 目录本文是第一份；
usage 只解析了 `prompt_tokens`（`ai_client.py:52`），`completion_tokens` / 缓存 / reasoning
token 全没取。

## 二、分层立场

**内核只提供能力，不决定内容。** 内核给一个写点位的接口和一个可替换的落地实现；
「记哪些字段、落到哪、日报读哪几列」是产品侧决定。

**内核只记 token 数与模型 id，不算钱。** 钱由报告层用带版本号的单价表算。理由是单价会变、
会有阶梯与缓存折扣，把金额烤进埋点意味着单价一改历史就不可比，且无法按新价重算。

### 为什么是扁平模块 `metrics.py`，不是包

仓库已有明确分界：`ai` / `session` / `gateway` 这些**包是组件**，有自己的进程或生命周期，
各自带 AGENTS.md；跨组件共享的**机制一律是顶层扁平模块**——`_appdata.py`(131 行)、
`_logging.py`(270 行)、`_sockets.py`(96 行)、`_workspace_paths.py`(198 行)。
metrics 是第四个这一类：session 要写、日后 gateway 也可能写，不属于任何一个组件。
体量也对得上，撑不到 150 行，切成包等于两个各几十行的文件，是「抽象名不副实」。

**命名不带下划线前缀**，用 `metrics.py`（与 `logs.py` / `protocol.py` 同列）。下划线那批是
内部机制，而 metrics 的调用方将来包括容器内 `workspace/tools/` 那一层（跨层 import），
下划线前缀在跨层契约上的意思是「不该被外面 import」。

后续真要加第二种 sink（sqlite / 网络上报）时再拆包，代价只有一次 import 改名。

## W：要什么

### 验收标准

1. 每个回合在 metrics jsonl 里**恰好一行**，含：时间戳、session id、回合序号、请求体字节数、
   工具数 N、工具数 M、首 token 相对耗时、整回合耗时、压缩是否触发及耗时、工具调用次数、结束原因
2. 同一行含成本原料：模型 id、`prompt_tokens`、`completion_tokens`、cached / 命中 tokens、
   reasoning tokens、以及**上游是否返回 usage 的标记**
3. 工具数必须记 **N 与 M 两个值**。只记一个则 `232 of 232`（收窄没生效）看不出来
4. 首 token 耗时必须是**真的首个 token**。不得用 `AI response status: 200`——那只有 50-60ms，
   量的是 litellm 立刻回的 SSE 响应头
5. 结束原因分 正常 / 超时 / 取消 / 异常 四值。**「未测到」与「零」不混**
6. 上游不返回 usage 时，token 字段记 `null` 并标记「未测到」，**不得记 0**。
   成本汇总里这类回合单独一栏，不静默算作 0 元
7. **压缩自身的 token 单独记一行**，不并进触发它的那个回合。曾实测压缩 41.5s × 22 次；
   并进去则单回合成本看着便宜而月账单对不上
8. 单价表落在仓库里，**带版本号与生效日期**；任何成本数字打印时必须带上用的是哪一版
9. log 侧：在能记原始 SSE 的位置旁补**一行 INFO 结构摘要**——有无 reasoning 字段、
   tool_calls 结构、content 前缀指纹。**不落原文**
10. 内核侧接口不含任何产品概念（不出现 feishu / haitun / 具体业务词），且**不含金额**
11. 运维群每天固定收到一份全量统计，**异常项排在最前面**，正常状态压成一行
12. 公网不可达 / OOM 两类在 **10 分钟内**告警，不等日报
13. **报告自身跑失败时，群里能收到「日报生成失败」**——不是安静
14. 每个指标带**基线与方向**，不是裸数字

### 不在范围内

- 不埋工具调用层（95 个工具，先拿回合与模型两层；数据量失控风险）
- 不做 trace（见结论先行）
- 不做预算熔断、超额自动停服（本期只观测与告警）
- 不做按人计费出账（本期只做归因维度，出账是另一回事）
- 不引入 Prometheus / Grafana（一机 7 容器、内存仅剩 2.6G）
- **不提升既有 DEBUG 日志级别**（见 A）
- 不做监控方案的第 4-7 类指标。**第 7 类明文密钥那条尤其不进日报**——会把一个未修的
  泄露点每天广播到运维群
- **不做成本对账**（负责人已定，见 H6）

## H：怎么做

### H1. 分层与落点

| 层 | 位置 | 约束 |
| --- | --- | --- |
| 内核埋点 | `src/psi_agent/metrics.py` | `record(event, **fields)` + 可替换 sink，默认 jsonl。字段由调用方传入。不含金额、不含产品词 |
| 报告层（算钱） | `deploy/haitun/monitoring/` | **纯标准库**，宿主 cron 直跑，**不 import 内核**——内核在容器里、日报在宿主，import 不过去 |
| 单价表 | `deploy/haitun/monitoring/pricing/` | 带 `version` 与 `effective_date` |
| 产品侧归因字段 | haitun 侧 | 如 `open_id`，内核不认识 |

### H2. jsonl 落盘

`{appdata}/metrics/{YYYY-MM-DD}.jsonl`，走 `resolve_appdata_root()`。

生产三个容器的 appdata 都 bind mount 到宿主可直接读的路径（已实测）：

| 容器 | 宿主路径 |
| --- | --- |
| gateway | `/srv/haitun/psi-agent/workspace/.psi/appdata/` |
| luolin | `/srv/haitun/psi-agent/workspace-luolin/.psi/appdata/` |
| chengxx | `/srv/haitun/psi-agent/workspace-chengxx/.psi/appdata/` |

只有 gateway 显式设了 `PSI_APPDATA=/workspace/.psi/appdata`；另两个没设，落回 platformdirs
默认，而容器内 `/root/.local/share/` 不存在——实际也写到了 `/workspace/.psi/appdata`。
日报**三份都读**（一人一容器是成本归因维度），**某一份缺失时报「未测到」而不是当 0**。

**按天分文件即轮转**，外加保留期。不复用 loguru 的轮转：日志轮转会吃掉历史，而成本汇总需要
跨天可读。

开关：默认开，`PSI_METRICS=0` 关。

**sink 不持文件句柄**，每次 append 开关一次。这是对草案 H5 第一条的直接规避——
「每会话把整个 workspace 重编一份」（实测每会话 114 文件、104 万字节），模块级单例若持有
句柄，可能变成每会话一个句柄同时追加同一文件。不持句柄就不需要先去确认这个行为。

### H3. 三种事件行

| event | 何时写 | 为什么这么切 |
| --- | --- | --- |
| `turn` | 回合结束 | 一行一回合 |
| `compaction` | 压缩结束 | **独立一行**，不并进触发它的回合（W#7） |

模型调用边界的字段（`ttft`、`req_bytes`、usage）**直接进 `turn` 行**，不单独出
`model_call` 事件：一个回合对应一次模型调用，拆两行只让报告层多做一次 join。

### H4. 采集点（只两层）

选这两层的理由：已知的慢与贵基本都落在这里——首字延迟已坐实 ≈ 请求体字节数 ÷ 上传带宽
（单流约 230KB/s）；工具 schema 实测 289774 字符，每回合都整份进 input，是成本的主项。

| 点位 | 文件 | 现状 |
| --- | --- | --- |
| ttft + req_bytes | `session/ai_client.py:152` | 已有 INFO，接线即可 |
| 工具 N / M | `session/tool_exposure.py:181` | 已有 INFO，接线即可 |
| 回合边界与结束原因 | `session/agent.py` 的 `_finish` | 已有四种 stop cause，正好对上四值 |
| usage 全套 | `session/ai_client.py:52` | 只取了 `prompt_tokens`，要扩成全套 + 缺失记 `null` |
| 压缩触发 / 结束 | `session/_compaction.py` | **零 logger，从零加** |

### H5. 七类指标里本期做哪三类

沿用监控方案的分类。**每个指标附「上次它怎么骗过我们」——这一列不能删**，否则后人会把
假阴性判据再写一遍。

#### 第 1 类：公网可达性（权重最高）

| 指标 | 上次它怎么骗过我们 |
| --- | --- |
| 每个 vhost 的公网 HTTPS 状态码 | 502 那 29 小时**容器内自检全绿**，只有从外面打才算数 |
| OAuth 回调路径实打一次 | 定时任务与发卡片走**出站**，回调走**入站**；内部全绿不证明入站活着 |
| TLS 证书剩余天数 | `caddy validate` 绿而 reload 失败，服务仍 active 跑旧配置，新 vhost 静默没生效 |
| 飞书长连接 wss 数 | **wss=0 只证明收不到，不证明发不出**——只起 gateway 也会真发飞书卡片 |
| 8090 探测 | `netns` 死了 8090 照样显示 LISTEN；`Up` 和 `LISTEN` 是两个并列的假阴性，只有**真打一次请求**算数 |

**硬要求**：用 `curl --resolve` 而非 `-H Host` 打裸 IP——后者 SNI 仍是 IP，TLS 层就 alert，
`HTTP=000` 与真 502 不可区分，会假报服务挂了。

#### 第 2 类：资源与 OOM

| 指标 | 上次它怎么骗过我们 |
| --- | --- |
| `dmesg` 里 OOM kill 计数 | gateway memcg OOM 撞 3g 时**三处判据全假阴性，只有 `dmesg` 靠得住** |
| 可用内存 / swap | A 机搬来 ToC 后可用仅 1.6G 且 `swappiness=0`；B 零 swap 而 A 有 4G |
| `sysctl` 中 swappiness 的**声明值** | 阿里云 `sysctl.d` 显式声明 0，`sysctl -w` 只改运行时、重启必回滚 |
| 各容器 memcg peak | 子进程被 OOM 杀掉时 `OOMKilled` 仍为 `false`，状态显示 Up，报错像上游问题，**零告警** |
| 磁盘 / inode | — |

#### 第 3 类：请求成本与延迟（从 metrics jsonl 读）

| 指标 | 上次它怎么骗过我们 |
| --- | --- |
| 每回合请求体**字节数** p50/p95 | 首字延迟 ≈ 字节数 ÷ 带宽（单流约 230KB/s），是最有解释力的单一指标 |
| `tools_exposed=N of M` **比值** | `232 of 232` 表示收窄没生效，但日志同时汇报「机制已启用」；**光看 N 看不出来** |
| 工具 schema 字符数 | 曾实测 289774，占不可裁地板约 47% |
| 首字延迟 | **不能用 `AI response status: 200`**——那只有 50-60ms，量的是 litellm 立刻回的 SSE 响应头。用 `turn` 行的 `ttft` 字段 |
| 压缩耗时与次数 | 曾实测 41.5s × 22 次，从 `compaction` 行读 |

### H6. 成本怎么算、怎么归因

- 金额 = Σ(各类 token × 对应单价)，**在报告层算**。缓存命中 token 单价不同，必须分开乘
- 归因维度：按会话、按容器（生产一人一容器）、按模型、按用途（正常回合 / 压缩）
- 日报的成本一节给四个数，**每个带基线与方向**：当日总花费、每回合成本 p50/p95、
  压缩占总花费比例、「未测到 usage」的回合数占比

三条硬要求：

1. 打印时**必须带单价表版本号**，且带「**未与账单对过**」字样。负责人已决定本期不做对账
   （对账要登上游控制台，无法自动化），这行字是唯一的诚实性保障
2. **缓存命中不省字节，只省钱。** 首字延迟是上传带宽决定的。这两件事在报告里**分节写，
   不要互相解释**
3. 「未测到 usage」的回合**不得静默算作 0 元**。报告要明说「N 个回合无 usage，
   总花费是下限」

### H7. 投递机制：报告不能跑在被监控对象里

**这是最容易做反的一条。**

故障史里最贵的一次是 gateway 502 持续 29 小时无人知晓。若日报靠 gateway 自己的
schedule runner 发，**gateway 挂了日报也挂了**——恰在最需要告警时静默。

- **宿主 cron + 独立出站 webhook**，不经 gateway、不经 psi-agent 任何进程
- 用飞书**自定义机器人 webhook URL**（纯 HTTP POST），不用 app token——app token 走 OAuth，
  而 OAuth 回调正是坏过的那条路
- cron 外包一层：**脚本非零退出即发「日报生成失败」**。没有这层，脚本挂掉表现为
  「群里安静」，与「一切正常」不可区分
- 即时档自身也要有**心跳兜底**，否则即时档自己死了同样是安静

两档：

| 档 | 频率 | 内容 | 理由 |
| --- | --- | --- | --- |
| 日报 | 每天一次，**非整点**（如 8:57） | 全量统计，慢变量 | 避免整点扎堆 |
| 即时 | 5-10 分钟 | 仅公网可达性 + OOM | 502 那次等一天 = 等 24 小时 |

**容器时区**：时区只由 compose 的 `TZ` 撑着，`/etc/localtime` 恒为 UTC 是假阴性。宿主 cron
用宿主时区，实现时必须在脚本里写明，否则会重演 cron 静默偏 8 小时。

复用 `deploy/haitun/audit-workspace-drift.sh`（139 行，已在仓库）覆盖投放漂移那一类，
本方案不重新设计这块。

### H8. 报告可读性

- **异常排最前，正常压一行。** 日报最大的失败模式不是数字错，是没人读
- **每个指标带基线与方向。** `232 of 232` 单看无异常，只有知道应是 66 才叫异常。
  没有基线的数字不会触发任何人的警觉
- **「未测到」与「零」两栏，不混。** 历史教训：量 `live render` 得 0 行，不是没渲染，
  是那行为 DEBUG 而生产跑 INFO——**观测缺口伪装成健康**

### H9. 其余已知坑

- **缓存不省字节**（见 H6 第 2 条）
- thinking 泄漏那条：`reasoning_content` 与 `reasoning` 逐字节相同**不是 bug**，
  结构摘要不要把它记成异常
- any-llm 的 deepseek provider 会主动注入 `thinking=disabled`。取 reasoning token 数时
  先确认该路径到底有没有这一项，**没有就记 `null` 不记 0**

## A：备选与否决

| 方案 | 否决理由 |
| --- | --- |
| metrics 做成包 `metrics/` | 仓库惯例是「组件才是包，跨组件机制是扁平模块」；体量撑不到 150 行，拆包是抽象名不副实 |
| 模块名带下划线前缀 | 调用方将来包括容器内 `workspace/tools/` 那层，跨层契约里下划线的意思是「不该被外面 import」 |
| 埋点时直接算好金额存进去 | 单价一改历史即不可比，且无法按新价重算；金额属产品决定，不进内核 |
| 单价写死在代码里、不带版本 | **硬编码清单当基线会把实测偷换成查表**——清单没跟上时，判据会用一句自信的错话指向错方向 |
| usage 缺失时记 0 | 观测缺口伪装成健康。「未测到」与「零」必须两栏 |
| 压缩 token 并进触发它的回合 | 单回合成本看着便宜而月账单对不上；压缩曾 41.5s × 22 次 |
| metrics 塞进现有日志 | 报告要 grep 捞，且日志轮转会吃掉历史 |
| metrics 落 SQLite | 并发写 + 多一份备份负担；psi-cloud 已是 SQLite |
| 全局开 DEBUG | 量大、原始请求体含用户内容与密钥新开泄露面；**且锚点选错时级别再低也只是把错的数看清楚**。另：生产走批量模式，级别钉死 INFO，本来就开不出来 |
| 埋点加在 haitun 侧 | 另一条产品线拿不到；双包拆分会让上游改动只跟到一侧 |
| 本期一并做 trace | 需贯穿 id 穿三层，内核边界未收敛，做不了增量 |
| 用 agent schedule 发日报 | **被监控对象挂了日报也挂**。本方案最核心的否决项 |
| Prometheus + Grafana | 一机 7 容器、内存仅剩 2.6G，监控栈本身成为新风险源；且需求是「每天一份统计」，不是实时时序 |
| 只做日报不做即时档 | 502 等一天 = 等 24 小时 |
| 用飞书 app token 发 | 多一层 OAuth 依赖，而 OAuth 回调正是坏过的那条路 |
| 用 `docker inspect` 的 `OOMKilled` 判 OOM | 子进程被杀时它仍为 `false` |
| 对账数字硬编码进仓库做自动判据 | 账单数字手工录入，会变成「硬编码清单当基线」那类反模式 |

## T：测试与判据

### 四条判据设计原则

1. **判据必须落在它声称的那一层。** 说测公网就从公网打，说测入站就真走入站。
   曾有 docstring 说测 AI 层却调 Session 层函数，变异复核也照不出来
2. **每个指标带「上次它怎么骗过我们」**（见 H5 各表）
3. **「未测到」与「零」分开报**
4. **数字带基线与方向**

### 必须有的判据

**埋点侧**

- 阴性用例：构造 N ≠ M 的情形，判据必须能区分。只看 N 的判据要能被这条打红
- 阴性用例：构造 N == M 且 M 是全量 → 必须报「收窄未生效」
- 阴性用例：模拟上游只回 SSE 响应头、迟迟不回 token。首 token 字段**不得**被填成响应头时刻
- 阴性用例：模拟上游不返回 usage。该回合必须进「未测到」栏，且当日总花费**不得**因此被
  低估无声
- 阴性用例：单价表换一版，同一批 jsonl 必须算出不同金额，且报告打印的版本号随之变
- 阴性用例：`metrics/` 目录整个不存在 → 报「未测到」并正常出日报其余部分，
  **不得整份脚本崩掉**（否则第一次部署就触发「日报生成失败」）
- 日志判据：**caplog 收不到 loguru 的日志**，要自己挂 `logger.add` sink，并同时记 level

**监控侧（三条负向判据是验收门槛）**

- 故意让脚本非零退出 → 群里收到「日报生成失败」
- 故意断一个 vhost → 即时档**一个周期内**告警
- 造一批缺 usage 的记录 → 日报必须报「未测到」而不是把总花费算低

**通用**

- **变异复核**：删掉首 token 采集、删掉 usage 采集，判据都必须转红。
  用 `cp` 备份还原，**不要用 `git checkout`**（会擦掉整份实现，且只有 `git diff --stat`
  为空才露马脚）
- 兜底链判据**用仓库里不存在的资源名**验证，不要用真名（目录在但内容不全会让兜底链提前
  终止，`isdir` 判据全绿抓不到）

### 跑测试的已知坑

- worktree 里 pytest **必须带 `PYTHONPATH=src`**，否则测的是主检出的 src
- 跑子树用 `-o testpaths=` 且**写在路径之前**，两种写错法都不报错、只是数字变大
- 全量失败数基线在 **57-62 间浮动**（Windows 上 asyncio 子进程 `NotImplementedError`，
  session 子树恒失败）。判回归前先用干净 worktree 做控制实验
- worktree 里 `ty check` **必须带 `--python`**，否则 768 个诊断而基线只有 4 个
- lint **看退出码不看 tail**（读还在缓冲的输出会报出全绿，CI 随即变红）
- 监控脚本**纯标准库**，宿主不装包

## 分卡与依赖

```
A 内核 metrics.py ──> B 采集点接线 ──> C 报告层 + log 结构摘要 ──┐
                                                               ├─> E 日报接 jsonl（第 3 类 + 成本节）
D 日报投递骨架 + 第 1、2 类 ───────────────────────────────────┘
```

| 卡 | 范围 | 触碰 |
| --- | --- | --- |
| A | `record()` + jsonl sink + 按天轮转 + 开关 | `src/psi_agent/metrics.py` |
| B | 四个点位接线；usage 扩全套；压缩点从零加 | `src/psi_agent/session/` |
| C | 单价表 + 算钱函数 + log 结构摘要 | `deploy/haitun/monitoring/`、`src/psi_agent/session/` |
| D | cron + webhook + 失败兜底 + 心跳；第 1、2 类 | `deploy/haitun/monitoring/` |
| E | 第 3 类指标 + 成本一节 | `deploy/haitun/monitoring/` |

D 与 A/B/C 全程并行且**文件不重叠**（D 只碰 `deploy/`，A/B 只碰 `src/`），避开
「并行卡跨文件改名，各自全绿、git 不报冲突、合完炸在收集期」那个坑。

各卡只 commit、**不开 PR、不开 auto-review**。由主会话合到 `feat/observability-and-monitoring`
统一提一个 PR。

生产投放（写 `/srv/haitun/` 下脚本目录、装两档 crontab）由负责人自己登 B 机执行，
不在卡的范围内。
